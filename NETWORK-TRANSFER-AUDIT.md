# Neon network transfer audit

Measured October 14, 2026 against the configured PostgreSQL database. The reported 4 GB of 5 GB monthly consumption is user-provided; historical Neon consumption was not accessible. No production data was modified by the audit, and the application changes below are local and not deployed.

## Did usage accumulate or spike?

Unknown. A cumulative 4 GB counter cannot distinguish weeks of normal traffic from a recent spike. PostgreSQL has no `pg_stat_statements` extension installed here, and there is no connected Neon management account or historical transfer series available in this session. Database creation/update timestamps do not reveal when reads occurred.

Check the Neon console's usage history for the current billing period, especially the last 48 hours, and correlate with deployment/API request logs and sync runs. If only a cumulative counter is available, record it now and again after 1, 6 and 24 hours. A 4 GB increase over 28 days averages 143 MB/day; over two days it averages 2 GB/day. These are illustrative rates, not observed usage.

Neon's public network transfer is outbound database traffic, not browser page size. Its consumption-history API documents hourly/daily metrics but requires an eligible paid plan; upgrading solely to run this audit is unnecessary. Sources: [Neon plans](https://github.com/neondatabase/website/blob/main/content/docs/introduction/plans.md), [consumption metrics](https://github.com/neondatabase/website/blob/main/content/docs/guides/consumption-metrics.md), [branch API eligibility](https://api-docs.neon.tech/reference/getconsumptionhistoryperbranchv2).

## Prioritized findings and changes

1. **Fixed: full reads for company counts and status discovery.** `/api/companies` and `/api/statuses` fetched all applications and leads, including large fields, then filtered ownership in JavaScript. They now filter ownership in SQL and return only company/owner references or status/history/owner references. Keeping status history preserves historical custom options. Dataset-wide payload proxies fall **99.1% for company references** and **97.8% for status references**, with additional savings from account filtering.
2. **Fixed: cross-account application over-fetching.** `/api/applications` now restricts reads to the signed-in account in SQL. Full details and logo precedence are retained for the UI. The legacy `user_ji` ownership rule for blank/`admin` owners is preserved; other administrators gain no broader access. Existing JavaScript filtering remains as defense in depth. Savings depend on each account's share of records and are not a fixed percentage. A cheap `EXISTS` check preserves the old globally-empty condition for Notion bootstrap.
3. **Fixed: unused logos in analytics reads.** Analytics already filtered ownership/scope in SQL and removed descriptions, information, notes and contacts. It still transferred large company logos that charts, aggregation, exports and insight-version calculation do not use. Removing that field reduces the dataset-wide analytics proxy **56.3%**, saving 587,571 B per complete dataset read. The saved role-fit analysis remains because deterministic statistics and saved-insight version checks consume it.
4. **Remaining: repeated analytics scans and aggregation.** Opening analytics triggers `/api/analytics` and `/api/analytics/insights`. Both call `getAccountAnalytics`, reading the same scoped records/preferences and computing deterministic aggregates in the application server. The insights path also reads the resume to build its version/context, even when only checking a saved report. Before this change the two dataset-wide analytics reads totaled about 2.086 MB; now about 911 KB. Prefer separating cheap version checks from full insight context, or reusing an authenticated snapshot. Preserve resume/preference changes, custom stage mappings, deduplication, response cohorts, salary groups and day-boundary aging. A SQL `COUNT(*)` replacement would not preserve these semantics.
5. **Remaining: authentication redundancies.** The JWT callback calls `getUserByEmail`; `getSessionAccount` calls it again. Both currently delegate to `getUsers`, which transfers the entire user table and may perform legacy cleanup. Parallel bootstrap endpoints amplify these reads. The application fetch effect depends on the whole session object, so session refreshes can also cause complete bootstrap reloads. Next improvement: targeted account lookup with equivalent normalization/cleanup and request-scoped reuse; keep immediate account revocation and authorization checks. Avoid a shared global account cache without explicit invalidation.
6. **Remaining: Notion recovery and full sync reads.** Page bootstrap automatically POSTs sync when the admin has fewer than five applications and Notion is connected. Every subsequent bootstrap can repeat this condition on a legitimately small dataset. Application/company GETs can also bootstrap empty datasets concurrently. Pull reads all existing applications/leads for matching; push reads all applications and checks eligibility per record; the POST response reads records again. Correlate POST counts with the suspected spike before altering recovery behavior. Next fix should deduplicate concurrent recovery and measure pending/eligible reads, while preserving retries and conflict/ownership protections.
7. **No recurring database polling loop found in the inspected app paths.** `DeploymentNotice` checks `/api/version` every minute; that endpoint has no database query or auth lookup. Analytics' minute timer changes the date locally and normally causes new reads only when the day changes. `jobstreet_sync --watch` runs every two seconds but refreshes local resume JSON. Session focus refreshes, UI mounts, preference edits, mutations and manual refresh/sync are distinct sources of repeated reads. External clients, production traffic, other branches, replication and database consoles remain unverified.
8. **Remaining: maintenance downloads.** `audit_postgres_duplicates.cjs` downloads and saves every complete application even in preview mode. Avoid scheduling it repeatedly; a counts-only duplicate preview could precede a deliberate backup. Runtime schema migration is already explicit rather than run on every request, so no evidence of a request-time schema-init loop was found.

## Expected improvement and verification

For one full application fetch, one company reference read and one status reference read, the dataset-wide JSON proxy drops from **4.771 MB to 1.640 MB: 65.6% less application/lead transfer**. This excludes company/user tables, auth, analytics, Notion traffic, account filtering and protocol overhead. It is a workload model, not a measured monthly reduction. Each 1,000 such cycles would avoid about 3.13 GB at today's dataset sizes before account filtering. Therefore repeated modest reads can plausibly consume gigabytes; the code alone does not prove a runaway process.

Validation: live company/status projections matched the previous JavaScript ownership filter for all six database accounts. Core tests covered isolation, lead lifecycle, company sharing, status history, analytics/export and Notion behavior. No AI dependency, shared response cache, database migration or infrastructure change was added.

Reproduce the read-only measurement with `node scripts/audit_network_transfer.cjs`; add `--verify` to exercise actual company/status queries and compare narrow references against the old ownership behavior. The verification downloads only reference fields and account identities internally; output contains aggregate results only. It does not measure historical usage.

Deploy through the normal release process, then compare transfer/hour and transfer per equivalent bootstrap/analytics/sync operation over 24–48 hours. Count requests by route and distinguish automatic recovery from manual sync. Compare similar traffic and record the billing-period reset; inspect every branch/client if traffic and transfer do not correlate. Optional sampling of query result bytes can help, but log only sizes, counts, operation names and anonymous identifiers, never SQL values, connection strings, resumes or application content.

**Do not recommend an infrastructure upgrade yet.** Apply and observe these query reductions first. If the sustained post-fix rate still projects beyond the remaining allowance before its reset, compare the cost of additional capacity with the measured remaining workload. More compute or connection pooling alone does not remove returned payload bytes.
