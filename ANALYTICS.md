# Analytics calculation and reliability

Analytics reads persisted applications, saved role-fit assessments, preferences, and status history. Loading, filtering, comparison tables, and PDF exports never require an AI key or provider. `POST /api/analytics/analyze` is called only by the interpretation button and receives server-computed statistics. Its validated output separates observations, implications and recommendations. Errors and timeouts leave charts, filters, exports, saved ratings, and the last successful interpretation available.

`GET /api/analytics?scope=ALL|INTERNSHIP|OTHER` uses `getAccountAnalytics` in `src/lib/analytics-service.ts`. PostgreSQL filters account ownership and job type before transferring records and excludes descriptions, notes, and contacts. The local JSON database follows the same ownership rules. Responses are private and uncached. Application saves, status changes, scope changes, preference changes, and reporting-day changes refresh the dashboard snapshot; no cache invalidation machinery or live inference is involved. A minute timer checks for a new date in Asia/Shanghai and refreshes only when that date changes. The dashboard can also calculate from its already-loaded saved records if the endpoint is unavailable. PDF export requests `GET /api/analytics?scope=...&format=export` for fresh saved records, preferences and computed statistics. It shows a retry message if that read fails. It neither reads saved interpretations nor invokes AI.

Aggregation remains in the shared deterministic TypeScript service to keep custom status mappings, historical phases, and recorded versus inferred progression consistent with chart drilldowns and exports. Each application's reached phase is computed once for the main pipeline. Comparison groups accumulate in one pass. This currently processes the selected account's records on the server; it does not materialize aggregates or claim constant database-query cost as an account grows. SQL aggregation can be introduced when measured volumes justify it, but must preserve the single source of truth in `analytics-stages.ts`. Migration adds owner/type/date, owner/status/source, owner/role-family, owner/platform/seniority indexes, plus ownership indexing for leads.

## Persisted application fields

`seniority_level` and `role_family` are derived from the title on creation and on title edits. Each has a corresponding `_source` field (`derived` or `manual`). The application form offers an Automatic seniority option and an editable role family with a reset button. Manual overrides survive title edits, status changes, Notion updates, and lead promotion. Sending a null value resets a field to automatic derivation. Legacy records without these fields derive on read and persist the values when next saved; analytics reads never modify records.

`job_platform` is user-selected text, with common platforms suggested in the form; custom names are supported. Older records fall back to their existing `source`, which remains available to integrations. `first_response_at` is an explicitly recorded employer response timestamp. The form shows browser-local time and saves an ISO timestamp in UTC. Blank values clear this explicit timestamp and leave response timing unknown. The migration adds nullable columns without overwriting historical data. Leads store the same fields in their existing JSON model.

The displayed label remains **Job platform**. Its suggestions include **Referral** and **Walk-in** for all users, including admins and members, and custom text is accepted. These offline channels must be selected manually: a posting URL cannot establish how a person discovered or applied to the job. Analytics groups saved values by casing-normalized text; the backfill preserves any existing nonempty selection.

## Timestamp audit and application maturity

The current database code writes `stage_history.at` on creation and status changes using the save time (`new Date().toISOString()`). These timestamps establish when tracking data was written; they are not verified employer response dates or interview dates. Analytics therefore uses only the actual saved `first_response_at` for response latency. There is no first-interview event timestamp in the existing application model, so time to interview remains Unknown. No interview date is inferred from an update or inferred funnel phase.

`analytics-timing.ts` derives calendar-day age from existing `date_applied` and an explicit reporting date. It never stores `application_age`. All submitted records receive an age distribution; active, currently submitted records without an explicit response or later phase receive a separate unanswered distribution. Offers, rejections, withdrawals, archived applications, interviews, screening and previously progressed records are excluded from unanswered aging even when response timing is unknown. Missing, invalid and future submission dates remain counted but have Unknown age. Bucket drilldowns show the actual age per application.

Saved preferences contain three increasing `analytics_age_boundaries` (default `[7,14,30]`). The resulting ranges are 0–7, 8–14, 15–30 and 31+ days, with no overlap. These are configurable display groups, not recruitment benchmarks. Changing them recomputes statistics without AI. Daily date changes refresh aging without altering any application record.

Average and median callback days use only valid paired submission/response dates; an unanswered application never contributes its waiting age to callback time. Fixed 7/14/30-day windows include only applications old enough to complete the entire window. Recent applications are excluded even if they already responded, preserving comparable observation periods. Mature records with missing event timing or a closed observation period are separately reported and excluded from the rate; they are not counted as no response. The eligible denominator consists of recorded responses with valid dates plus applications still unanswered according to saved records. Missing submission dates are excluded. These are recorded-data rates subject to reporting completeness, not estimates of future response chances.

## Counting rules

- Role families use saved manual overrides or Unicode normalization, punctuation/whitespace cleanup, seniority-token removal, and exact aliases in `ROLE_ALIASES` in `application-analytics-fields.ts`. `normalizedRole` also accepts a custom alias map. Titles are never sent to a classifier.
- Seniority has eight values: Internship / Trainee, Graduate / Entry-level, Junior, Associate, Mid-level, Senior, Lead / Principal, and Unspecified. Only explicit title keywords establish an automatic level. `Junior AI Engineer` is Junior; `AI Engineer` is Unspecified. Job descriptions are not consulted and missing Junior never implies Mid-level.
- Saved role-fit ratings take precedence over saved assessment results, including manual overrides. Missing or invalid ratings are Unassessed. Qualifications comparisons reuse this rating as an experience-alignment proxy; the model stores no separate numerical qualifications-match score. Preference alignment remains its own chart.
- Platform uses the saved `job_platform`, falling back to the stored source, with missing sources Unknown. Grouping ignores casing. Progression and offers use the existing shared phase mapping; offer-stage evidence is not proof of a verified salary offer.
- Callback timing uses saved `first_response_at` only. Current status, status-history save timestamps, update timestamps, withdrawals, and inferred phases do not establish a response date. Invalid, future, or pre-submission responses are excluded. Average and median calculations exclude unknown latency; records stay included in aggregate counts. Calendar days use the project's Asia/Shanghai reporting timezone.
- Response cohorts group by the stored submission month, counting recorded responses through the report date. Missing submission dates form an Unknown cohort. Newer cohorts have had less time to respond. Recorded-response rates are limited by history completeness.
- Existing fit groups provide role-fit calibration against progression, offers, and rejections. Role, seniority, platform, cohort, and saved-fit comparisons show application effectiveness without inventing a composite score or causal claim.
- The dashboard and PDF share visual summaries of pipeline, effectiveness, timing, and career insights. The normal report is four pages; category charts show the largest submitted samples and disclose omitted groups. Long preference targets or extra salary units can add an appendix. AI interpretations and AI placeholders are excluded entirely. Reports contain no application notes, descriptions, contacts, or resume text.

## Visual reporting

The PDF and dashboard use the same deterministic display data. Automatic title families can be grouped into AI / ML Engineering, Software Development, Automation / RPA, Data / Analytics, IT Support, and Business / Operations; unmatched families keep their label. Manual families and original titles are preserved. This is a reporting view, not a stored reclassification or a change to existing calculations. Full original-family, seniority, platform, cohort, and fit tables remain available in Analytics.

Performance charts exclude groups with no submissions, display application counts without statistical notation, and describe samples below five as based on limited application data. Counts remain in tooltips and calculation details; labels avoid repeating counts already displayed. Role-fit stacked bars show exclusive current outcomes among submitted applications; offer-stage conversion remains a separate measure, including declined offers. Recorded salary offers are labeled separately from offer-stage evidence.

Callback histograms use valid saved submission/response pairs in calendar days. The cohort heatmap appears with at least five usable responses across two submission months; its cells count responses, not conversion rates. A single response stays in the KPIs without a distribution chart. Missing timing produces a concise empty state; response-window coverage bars explain eligible, too-recent, and unknown-timing samples while the heatmap is unavailable. Unanswered aging uses saved configurable boundaries; 7/14/30-day response windows keep their existing maturity and unknown-timing exclusions.

Career charts and the PDF separate deterministic findings, limitations and suggested actions. Optional AI interpretation has its own card above the charts. Salary bullets compare recorded medians within the same currency and pay period; only monthly groups in the target currency show the monthly minimum. Matched expectation gaps still pair the same application. Long saved preference text is paginated rather than clipped. Combining scopes does not make historical internships equivalent to recent non-internship applications.

The PDF embeds the original transparent `public/job-hunt official text.png` at its native aspect ratio in every header. It uses A4 portrait, consistent margins, baby-pink accents, readable labels, and date/page footers. Charts and KPI groups stay on their assigned pages.

## Optional saved pipeline insights

The card immediately below the header is compact before analysis and expandable afterward. It shows **What stands out?**, **What does this mean?**, and **What can I do next?**, with up to three cards per section and verified evidence. Generation time, scope and an outdated label distinguish saved interpretations from current calculations. Loading and changing scopes only read saved results; they never regenerate them.

The authenticated POST derives scope-specific statistics and reads the same account's master resume, saved role-fit assessments, manual overrides and career preferences. Missing resumes or callback dates are limitations. Employer contact details, application notes, descriptions, company names, record IDs and individual salary records are excluded from the model context; known candidate/contact details are removed from supplied text. Resume and imported content are treated as untrusted data. Detailed context is bounded to the latest two hundred updated records and largest twelve comparison groups; aggregate counts include the whole scope, with a limitation when details are truncated.

The response schema validates bounded text, section sizes, metric references and exact numerical claims. Prose contains no numerals or percentages; displayed quantities come from computed evidence. Validation cannot prove every sentence's meaning, so the prompt also forbids predictions, causal claims, invented quantities and unsupported comparisons. Scope, timestamp and snapshot version are assigned by the server. Invalid responses and provider failures return a safe message without exposing raw JSON or logging model text.

Successful reports are saved in `candidate_profiles.pipeline_insights`, keyed by ALL, INTERNSHIP or OTHER; local profiles use the same structure. A snapshot hash includes application data, preferences, the saved master resume and reporting date. `GET /api/analytics/insights?scope=...` reads only the signed-in account and reports whether the saved hash is outdated. A guarded database lease prevents simultaneous requests for the same account/scope, expires after a stalled request, and preserves the previous report until a replacement validates and saves. The client blocks repeated clicks. Profile/resume and preference writes preserve stored insights.

## URL platform backfill

`npm run rpa:job-platforms:preview` plans a deterministic backfill for the account matching the configured administrator email. `npm run rpa:job-platforms` applies it to that account's applications and leads. To select an account explicitly, run `node scripts/backfill_job_platforms.cjs --owner ACCOUNT_ID_OR_EMAIL` with optional `--apply`.

The local hostname registry in `job-platform.ts` recognizes job boards, ATS hosts, and listed employer career sites. An employer website stored on a company can also establish a direct-site match. Unknown domains, missing URLs, email addresses, and shortened links remain unclassified; no URLs are opened and no AI is called. Domain boundaries prevent a tracking parameter or lookalike domain from selecting a platform. The URL establishes the destination platform, not an unrecorded referral source.

Existing nonempty platform selections are preserved. Updates affect only `job_platform` and the normal update timestamp; they do not change submission dates, hiring history, assessments, statuses, or Notion sync settings. PostgreSQL updates use account-scoped snapshots and guards for URL, ownership, platform and exact timestamp; lead updates compare the original JSON. PostgreSQL timestamps are read as text to preserve microseconds in the concurrency guard. Only an additive `job_platform` column is created if missing; unrelated schema migrations are not run. Local storage saves a full pre-update backup and checks for concurrent changes before an atomic replacement. Reports and prior changed-field values are saved under `.data/job-platform-backfill-*`.

Run `npm run test:job-platforms` to check URL classification, selected-platform preservation, account isolation, repeated-run safety and guarded writes.

## Verification commands

`npm run test:pipeline` covers deterministic metrics with unavailable AI, missing keys, timeouts, scope changes, additions and status updates, incomplete history, normalization, age boundaries, maturity-adjusted response windows, callback timing, daily age changes, and PDF output. It also checks malformed insights, numerical claim validation, privacy, nontechnical roles, missing resumes, owner isolation and guarded persistence. PDF tests check branded A4 headers, transparency, text bounds, long labels, missing data, larger datasets and exclusion of AI content. `npm run test:analytics:ui` targets a running development server at `http://localhost:3100` (override with `PIPELINE_TEST_URL`), mocks network endpoints, and verifies zero automatic assessment calls, age drilldowns, preference-controlled ranges, PDF/filter availability during interpretation, saved and outdated scope-specific reports, and preservation of the last interpretation after errors.

Optional local historical inventory: `references/analytics/current-analytics.txt`. It describes a supplied earlier report, not the current dashboard or live totals. The `references/` directory is ignored by Git; current maintained calculation guidance is in this file.
